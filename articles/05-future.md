## Linear types

Линейный тип — это тип, значение которого нужно использовать ровно один раз.
Код, получивший такое значение, должен потребить его или передать владение дальше.
Владение в Rust описывается аффинными типами:
значение можно использовать не более одного раза, но можно и не использовать.

### Проблема: резерв можно оставить без обработки

В конце части 4 мы остановились на `WorkingOrder`:
можно получить заявку в этом состоянии и выйти из функции, не вызвав ни `fill`, ни `cancel`.
С резервом маржи возникает похожая задача.
После резервирования нужно либо закрепить средства за заявкой, либо освободить их.

Представим резерв отдельным объектом с двумя методами:

```rust
struct MarginReservation {
    // Данные резерва.
}

impl MarginReservation {
    fn commit(self) {
        // Закрепить резерв за заявкой.
    }

    fn release(self) {
        // Освободить резерв.
    }
}
```

Оба метода принимают `self` по значению, как переходы typestate из части 1.
Сам учёт средств здесь опущен: нас интересует, обязан ли владелец вызвать один из методов.
Пока ничто не мешает написать такую функцию:

```rust
fn process_order(_reservation: MarginReservation) {
    // Ни commit, ни release не вызваны.
}
```

Код компилируется.
При выходе из функции Rust уничтожит локальный объект.
В нашем примере ни закрепление, ни освобождение резерва при этом не выполняется.

### Решение: значение нужно обязательно использовать ровно один раз

Для нашего резерва нужно запретить выход из функции без обработки объекта.
В [обсуждаемом дизайне](https://goals.rust-lang.org/2026/move-trait.html)
для этого предлагаются ограничения на забывание и уничтожение значения.
Это изменения языка.
На выбранном nightly эти ограничения пока не проверяются.

Сейчас Rust уничтожает локальный резерв при выходе из функции,
если тот не был передан дальше.
Уничтожение включает вызов [`Drop::drop`](https://doc.rust-lang.org/std/ops/trait.Drop.html),
если он реализован, и уничтожение полей значения.
[`drop(reservation)`](https://doc.rust-lang.org/std/mem/fn.drop.html) делает это сразу.

[`mem::forget(reservation)`](https://doc.rust-lang.org/std/mem/fn.forget.html) забирает владение,
но пропускает уничтожение: ни `Drop::drop`, ни очистка полей не выполняются.
Переданный резерв после этого уже нельзя использовать.
Если бы в `Drop` было автоматическое освобождение резерва,
вызов `mem::forget` позволял бы пропустить и его.

Два трейта описывают разные разрешения:

| Трейт | Что разрешает |
| --- | --- |
| `Forget` | Пропустить уничтожение через `mem::forget(reservation)` |
| `Destruct` | Уничтожить резерв через `drop(reservation)` или при выходе из функции |

Для нашего API нужно потребовать явного вызова `commit` или `release`.
Поэтому резерв не должен разрешать ни забывание, ни обычное уничтожение.
Запись `impl !Forget` приведена в цели проекта.
Для `Destruct` в этом примере также нужен запрет;
ниже оба ограничения записаны схематично, окончательный синтаксис ещё обсуждается.

```rust
// Иллюстративный синтаксис; это не работающий пример на выбранном nightly.
impl !Forget for MarginReservation {}
impl !Destruct for MarginReservation {}
```

В такой модели первая версия `process_order` отклонялась бы компилятором:
функция заканчивается с необработанным резервом.

Решение по заявке передадим отдельным типом `OrderDecision`:

```rust
enum OrderDecision {
    Accept,
    Reject,
}

fn process_order(reservation: MarginReservation, decision: OrderDecision) {
    match decision {
        OrderDecision::Accept => reservation.commit(),
        OrderDecision::Reject => reservation.release(),
    }
}
```

`commit` и `release` должны разобрать `self` и обработать данные резерва.
С пустым телом `self` уничтожался бы в конце метода, что запрещено при `!Destruct`.

### Что можно сделать на stable

На stable для работы с забытым резервом можно использовать `Drop` и `#[must_use]`.

В `Drop` можно автоматически освобождать необработанный резерв.
Если вызывающий код выйдет из `process_order`, не вызвав ни `commit`, ни `release`,
средства освободятся при уничтожении резерва.
Такой API выбирает освобождение по умолчанию и подходит,
если это соответствует правилам системы и резерв можно освободить синхронно.
Если освобождение требует асинхронного запроса на биржу,
дождаться его через `.await` в обычном `Drop` нельзя: async drop на stable пока нет.
Компилятор при этом не требует явного решения от владельца резерва.

Если пометить `MarginReservation` атрибутом `#[must_use]`,
компилятор предупредит о проигнорированном результате функции, возвращающей резерв.
Но сохранение резерва в переменную уже считается использованием для этой проверки.
Затем можно оставить его до конца функции, так и не вызвав `commit` или `release`.
Атрибут не проверяет, как завершена работа с полученным значением.

## Ordered types

Упорядоченные типы требуют использовать значения ровно один раз и в порядке их введения.
В Rust это связано с неподвижностью значения:
его адрес в памяти не меняется до уничтожения.

### Проблема: самоссылочные структуры

Самоссылочная структура содержит ссылку на собственные данные.
Если переместить такую структуру в памяти, её поля окажутся по новым адресам,
а сохранённая ссылка продолжит указывать на прежний адрес.

Такие структуры возникают и в обычном async-коде.
Вызов `async fn` создаёт future; тело функции начинает выполняться при его опросе.
Компилятор преобразует тело в машину состояний:
она хранит данные, которые понадобятся после приостановки, и точку продолжения выполнения.
Если среди этих данных есть ссылка на другую локальную переменную,
future может оказаться самоссылочным.

В части 2 мы обсуждали асинхронный вариант `ExchangeClient`:

```rust
trait ExchangeClient {
    async fn submit_order(&self, order: &DraftOrder) -> Result<OrderId, ExchangeError>;
}
```

Функция отправки владеет заявкой и передаёт клиенту ссылку на неё.
После успешного ответа запишем в лог клиентский идентификатор заявки:

```rust
async fn place_order(
    exchange_client: &impl ExchangeClient,
    draft: DraftOrder,
) -> Result<OrderId, ExchangeError> {
    let order = &draft;
    let exchange_id = exchange_client.submit_order(order).await?;
    println!("Биржа приняла заявку {}", order.client_order_id().0);
    Ok(exchange_id)
}
```

Пока биржа не ответила, выполнение может приостановиться на `.await`.
Ссылка `order` нужна и для отправки, и для логирования после ответа.
Она должна оставаться действительной между этими шагами.

Назовём созданный компилятором тип future `OrderSubmission`.
Схематично его состояние во время ожидания выглядит так:

```text
OrderSubmission
  draft: DraftOrder
  order: ссылка на draft внутри этого же OrderSubmission
  pending: future вызова submit_order(order)
  state: ожидание ответа биржи
```

Внешний future хранит заявку, ссылку на неё и вложенный future отправки.
При следующем опросе он продолжит выполнение с сохранёнными данными.
Перемещение всего `OrderSubmission` могло бы сделать ссылку `order` недействительной.

Неподвижность нужна самоссылочному состоянию future.
Та же задача возникает в других async-функциях,
которые сохраняют заимствования собственных данных между приостановками.

### Что обеспечивает `Pin` сейчас

Показанный код работает на stable.
В текущем Rust стабильность адреса таких future обеспечивается через
[`Pin`](https://doc.rust-lang.org/std/pin/index.html).
Метод [`Future::poll`](https://doc.rust-lang.org/std/future/trait.Future.html)
принимает закреплённую ссылку:

```rust
trait Future {
    type Output;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

`poll` возвращает `Poll::Pending`, если операция ещё не завершена,
или `Poll::Ready` с результатом.
При следующем опросе выполнение продолжается с сохранёнными данными.
До начала выполнения future из `async fn` можно перемещать:
внутренние ссылки ещё не созданы.
Для вызова `poll` future сначала закрепляют.
При обычном `.await` это происходит без явного `Pin` в пользовательском коде.

Для future из `async fn` и async-блоков компилятор сам задаёт отсутствие `Unpin`.
Другие реализации `Future` могут быть `Unpin`,
например [`Ready<T>`](https://doc.rust-lang.org/std/future/fn.ready.html).

Если тип не реализует `Unpin`,
безопасный API `Pin` не позволяет извлечь закреплённое значение и переместить его.
Сам указатель при этом можно передавать дальше: адрес значения от этого не меняется.
`!Unpin` само по себе не запрещает перемещения до закрепления.

`Pin` компенсирует отсутствие в языке неподвижных типов через библиотечный контракт.
Создание `Pin` не меняет правила перемещения значения для компилятора.
Гарантию поддерживают ограничения безопасного API и корректность его `unsafe`-реализации.
Для future из `async fn` необходимые действия выполняет сгенерированный компилятором код.

При ручной реализации обёртки над future эта работа становится видна.
Из `Pin<&mut Outer>` нужно получить `Pin<&mut Inner>`, чтобы вызвать `poll` вложенного future.
Обычного заимствования поля для этого недостаточно:
нужно обеспечить, что поле тоже останется неподвижным.
Такую операцию называют проекцией закреплённой ссылки.
Для полей без `Unpin` её обычно реализуют через `unsafe` или макросы,
которые генерируют этот код.

Требование закрепления влияет и на интерфейсы.
У `Future` оно уже выражено в сигнатуре `poll`,
но у `Iterator::next` используется обычный `&mut self`.
Для обобщённой работы с неподвижными итераторами приходится обсуждать отдельный интерфейс
или изменение способа выразить неподвижность.
Эту проблему Yosh Wuyts разбирает в
[посте о `Pin` в сигнатурах трейтов](https://blog.yoshuawuyts.com/why-pin/).

### Решение: неподвижность как свойство типа

В [предложении о неподвижных типах](https://github.com/rust-lang/rust/issues/149607)
`Move` описывает разрешение перемещать значение в памяти.
Тип с `!Move` должен сохранять адрес на протяжении всего своего существования.
Компилятор проверял бы это свойство при операциях со значением.
Условия уничтожения и забывания задаются отдельно через `Destruct` и `Forget`.

В [варианте преобразования async-кода, описанном Yosh Wuyts](https://blog.yoshuawuyts.com/self-referential-types/),
компилятор сам создавал бы неподвижное состояние future.
Для нашего `OrderSubmission` соответствующая часть сгенерированного кода выглядела бы так:

```rust
// Схема будущего кода компилятора, не работающий пример на выбранном nightly.
impl !Move for OrderSubmission {}
```

Такое состояние нельзя было бы перенести в другую переменную или передать по значению в функцию.
Операции вроде `mem::replace`, позволяющие вынуть значение через `&mut`,
тоже должны учитывать ограничение `Move`.
Неподвижность была бы свойством самого значения,
поэтому API для работы с ним мог бы использовать обычные ссылки.
При работе с вложенным неподвижным значением можно было бы заимствовать его поле.

Значение с `!Move` нужно сразу создавать по адресу, который оно будет занимать до уничтожения.
Обычный возврат значения из конструктора допускает перемещение в память вызывающего кода.
Для неподвижного типа нужно гарантировать создание сразу в этой памяти.
Такое создание называют
[in-place initialization](https://blog.yoshuawuyts.com/placing-functions/).

У нынешнего future неподвижность требуется после закрепления,
а у предлагаемого `!Move` она действует с момента создания.
Поэтому добавить `!Move` к существующему async-коду и убрать `Pin` недостаточно:
нужно согласовать создание future и интерфейс его выполнения с новыми правилами.

### Статус фич

Неподвижные типы и гарантии уничтожения входят в
[принятую цель Rust на 2026–2027 годы](https://goals.rust-lang.org/2026/move-trait.html).
Дизайн ещё обсуждается.
Примеры с `MarginReservation` выше показывают обычный Rust и желаемую проверку.
Схема с `!Forget` и `!Destruct` иллюстрирует требуемые ограничения.
Синтаксис отрицательного `impl` для `Forget` приведён в цели проекта;
запись с `!Destruct` здесь показывает желаемое свойство типа.
Добавить эти строки к примеру и получить такую проверку на выбранном nightly пока нельзя.

В [предложении Niko Matsakis](https://smallcultfollowing.com/babysteps/blog/2025/10/21/move-destruct-leak/)
трейты связаны иерархией `Forget: Destruct: Move`.
Текущая цель проекта рассматривает другой вариант:
неподвижное значение тоже может нуждаться в уничтожении,
поэтому `Destruct` не должен обязательно требовать `Move`.

Изменение существующего `Future` не входит в эту цель проекта.
Переход от `Pin` к `Move` для async-кода потребует отдельного решения.

## Function contracts

Основной пример: резервируем `quantity` лотов из доступного объёма `available`.
Предусловие: `quantity > 0 && quantity <= available`.
Постусловие: остаток равен `available - quantity`.
Сравнить с проверками внутри функции и smart constructors из части 1.
Объяснить, почему тип ненулевого объёма не выражает отношение двух независимых аргументов.
Входящие данные сначала проходят обычную обработку ошибок;
контракт проверяет договорённости между внутренними компонентами.

Эксперимент [`contracts`](https://doc.rust-lang.org/nightly/unstable-book/language-features/contracts.html)
уже описан в Unstable Book;
[`-Z contract-checks`](https://doc.rust-lang.org/nightly/unstable-book/compiler-flags/contract-checks.html)
включает проверки в рантайме.
Проверенный вариант использует `core::contracts::{requires, ensures}`
и `move`-замыкание постусловия, которое захватывает числовые аргументы.
На выбранном nightly нарушение предусловия приводит к abort;
`Result` контракт не возвращает.
Описанные проверки не доказывают условия при компиляции.

Хорошая модель домена — это не та, где можно выразить всё подряд.
Скорее наоборот: та, в которой трудно сделать неправильную вещь.
Если модель строится вокруг примитивов и независимых полей, типы обычно позволяют больше, чем реально существует в предметной области.
Тогда ограничения начинают жить отдельно — в if-ах, документации, комментариях и негласных договорённостях вроде «этот метод не вызывай после cancel».
Получается разрыв: типы разрешают больше состояний, чем существует в модели.

Type-driven подход пытается этот разрыв закрыть.
Типы начинают описывать не только форму данных, но и правила игры: какие состояния возможны, какие комбинации допустимы, какие переходы разрешены.
У этого есть цена. Типов становится больше, модель — подробнее, а код многословнее.
Но сложность не исчезает — она просто переезжает: из runtime-проверок в систему типов.
Вместо «не забудь проверить этот кейс» появляется ошибка компиляции.
Вместо документации в духе «сюда передавай только валидное состояние» — интерфейс, который не даёт передать невалидное.
