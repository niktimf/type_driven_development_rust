## Linear types

Линейный тип — это тип, значение которого нужно использовать ровно один раз.
Код, получивший такое значение, должен потребить его или передать владение дальше.
Владение в Rust описывается аффинными типами:
значение можно использовать не более одного раза, но можно и не использовать.

### Проблема: резерв можно оставить без обработки

В конце части 4 мы остановились на `WorkingOrder`:
можно получить заявку в этом состоянии и выйти из функции, не вызвав ни `fill`, ни `cancel`.
С резервом маржи возникает похожая задача.
После резервирования нужно либо закрепить средства за заявкой, либо освободить их.

Представим резерв отдельным объектом с двумя методами:

```rust
struct MarginReservation {
    // Данные резерва.
}

impl MarginReservation {
    fn commit(self) {
        // Закрепить резерв за заявкой.
    }

    fn release(self) {
        // Освободить резерв.
    }
}
```

Оба метода принимают `self` по значению, как переходы typestate из части 1.
Сам учёт средств здесь опущен: нас интересует, обязан ли владелец вызвать один из методов.
Пока ничто не мешает написать такую функцию:

```rust
fn process_order(_reservation: MarginReservation) {
    // Ни commit, ни release не вызваны.
}
```

Код компилируется.
При выходе из функции Rust уничтожит локальный объект.
В нашем примере ни закрепление, ни освобождение резерва при этом не выполняется.

### Решение: значение нужно обязательно использовать ровно один раз

Для нашего резерва нужно запретить выход из функции без обработки объекта.
В [обсуждаемом дизайне](https://goals.rust-lang.org/2026/move-trait.html)
для этого предлагаются ограничения на забывание и уничтожение значения.
Это изменения языка.
На выбранном nightly эти ограничения пока не проверяются.

Сейчас Rust уничтожает локальный резерв при выходе из функции,
если тот не был передан дальше.
Уничтожение включает вызов [`Drop::drop`](https://doc.rust-lang.org/std/ops/trait.Drop.html),
если он реализован, и уничтожение полей значения.
[`drop(reservation)`](https://doc.rust-lang.org/std/mem/fn.drop.html) делает это сразу.

[`mem::forget(reservation)`](https://doc.rust-lang.org/std/mem/fn.forget.html) забирает владение,
но пропускает уничтожение: ни `Drop::drop`, ни очистка полей не выполняются.
Переданный резерв после этого уже нельзя использовать.
Если бы в `Drop` было автоматическое освобождение резерва,
вызов `mem::forget` позволял бы пропустить и его.

Два трейта описывают разные разрешения:

| Трейт | Что разрешает |
| --- | --- |
| `Forget` | Пропустить уничтожение через `mem::forget(reservation)` |
| `Destruct` | Уничтожить резерв через `drop(reservation)` или при выходе из функции |

Для нашего API нужно потребовать явного вызова `commit` или `release`.
Поэтому резерв не должен разрешать ни забывание, ни обычное уничтожение.
Запись `impl !Forget` приведена в цели проекта.
Для `Destruct` в этом примере также нужен запрет;
ниже оба ограничения записаны схематично, окончательный синтаксис ещё обсуждается.

```rust
// Иллюстративный синтаксис; это не работающий пример на выбранном nightly.
impl !Forget for MarginReservation {}
impl !Destruct for MarginReservation {}
```

В такой модели первая версия `process_order` отклонялась бы компилятором:
функция заканчивается с необработанным резервом.

Решение по заявке передадим отдельным типом `OrderDecision`:

```rust
enum OrderDecision {
    Accept,
    Reject,
}

fn process_order(reservation: MarginReservation, decision: OrderDecision) {
    match decision {
        OrderDecision::Accept => reservation.commit(),
        OrderDecision::Reject => reservation.release(),
    }
}
```

`commit` и `release` должны разобрать `self` и обработать данные резерва.
С пустым телом `self` уничтожался бы в конце метода, что запрещено при `!Destruct`.

### Что можно сделать на stable

На stable для работы с забытым резервом можно использовать `Drop` и `#[must_use]`.

В `Drop` можно автоматически освобождать необработанный резерв.
Если вызывающий код выйдет из `process_order`, не вызвав ни `commit`, ни `release`,
средства освободятся при уничтожении резерва.
Такой API выбирает освобождение по умолчанию и подходит,
если это соответствует правилам системы и резерв можно освободить синхронно.
Если освобождение требует асинхронного запроса на биржу,
дождаться его через `.await` в обычном `Drop` нельзя: async drop на stable пока нет.
Компилятор при этом не требует явного решения от владельца резерва.

Если пометить `MarginReservation` атрибутом `#[must_use]`,
компилятор предупредит о проигнорированном результате функции, возвращающей резерв.
Но сохранение резерва в переменную уже считается использованием для этой проверки.
Затем можно оставить его до конца функции, так и не вызвав `commit` или `release`.
Атрибут не проверяет, как завершена работа с полученным значением.

## Ordered types

Упорядоченные типы требуют использовать значения ровно один раз и в порядке их введения.
В Rust это связано с неподвижностью значения:
его адрес в памяти не меняется до уничтожения.

### Проблема: самоссылочные структуры

Самоссылочная структура содержит ссылку на собственные данные.
Если переместить такую структуру в памяти, её поля окажутся по новым адресам,
а сохранённая ссылка продолжит указывать на прежний адрес.

Такие структуры возникают и в обычном async-коде.
Вызов `async fn` создаёт future; тело функции начинает выполняться при его опросе.
Компилятор преобразует тело в машину состояний:
она хранит данные, которые понадобятся после приостановки, и точку продолжения выполнения.
Если среди этих данных есть ссылка на другую локальную переменную,
future может оказаться самоссылочным.

В части 2 мы обсуждали асинхронный вариант `ExchangeClient`:

```rust
trait ExchangeClient {
    async fn submit_order(&self, order: &DraftOrder) -> Result<OrderId, ExchangeError>;
}
```

Функция отправки владеет заявкой и передаёт клиенту ссылку на неё.
После успешного ответа запишем в лог клиентский идентификатор заявки:

```rust
async fn place_order(
    exchange_client: &impl ExchangeClient,
    draft: DraftOrder,
) -> Result<OrderId, ExchangeError> {
    let order = &draft;
    let exchange_id = exchange_client.submit_order(order).await?;
    println!("Биржа приняла заявку {}", order.client_order_id().0);
    Ok(exchange_id)
}
```

Пока биржа не ответила, выполнение может приостановиться на `.await`.
Ссылка `order` нужна и для отправки, и для логирования после ответа.
Она должна оставаться действительной между этими шагами.

Назовём созданный компилятором тип future `OrderSubmission`.
Схематично его состояние во время ожидания выглядит так:

```text
OrderSubmission
  draft: DraftOrder
  order: ссылка на draft внутри этого же OrderSubmission
  pending: future вызова submit_order(order)
  state: ожидание ответа биржи
```

Внешний future хранит заявку, ссылку на неё и вложенный future отправки.
При следующем опросе он продолжит выполнение с сохранёнными данными.
Перемещение всего `OrderSubmission` могло бы сделать ссылку `order` недействительной.

Неподвижность нужна самоссылочному состоянию future.
Та же задача возникает в других async-функциях,
которые сохраняют заимствования собственных данных между приостановками.

### Что обеспечивает `Pin` сейчас

Показанный код работает на stable.
В текущем Rust стабильность адреса таких future обеспечивается через
[`Pin`](https://doc.rust-lang.org/std/pin/index.html).
Метод [`Future::poll`](https://doc.rust-lang.org/std/future/trait.Future.html)
принимает закреплённую ссылку:

```rust
trait Future {
    type Output;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

`poll` возвращает `Poll::Pending`, если операция ещё не завершена,
или `Poll::Ready` с результатом.
При следующем опросе выполнение продолжается с сохранёнными данными.
До начала выполнения future из `async fn` можно перемещать:
внутренние ссылки ещё не созданы.
Для вызова `poll` future сначала закрепляют.
При обычном `.await` это происходит без явного `Pin` в пользовательском коде.

Для future из `async fn` и async-блоков компилятор сам задаёт отсутствие `Unpin`.
Другие реализации `Future` могут быть `Unpin`,
например [`Ready<T>`](https://doc.rust-lang.org/std/future/fn.ready.html).

Если тип не реализует `Unpin`,
безопасный API `Pin` не позволяет извлечь закреплённое значение и переместить его.
Сам указатель при этом можно передавать дальше: адрес значения от этого не меняется.
`!Unpin` само по себе не запрещает перемещения до закрепления.

`Pin` компенсирует отсутствие в языке неподвижных типов через библиотечный контракт.
Создание `Pin` не меняет правила перемещения значения для компилятора.
Гарантию поддерживают ограничения безопасного API и корректность его `unsafe`-реализации.
Для future из `async fn` необходимые действия выполняет сгенерированный компилятором код.

При ручной реализации обёртки над future эта работа становится видна.
Из `Pin<&mut Outer>` нужно получить `Pin<&mut Inner>`, чтобы вызвать `poll` вложенного future.
Обычного заимствования поля для этого недостаточно:
нужно обеспечить, что поле тоже останется неподвижным.
Такую операцию называют проекцией закреплённой ссылки.
Для полей без `Unpin` её обычно реализуют через `unsafe` или макросы,
которые генерируют этот код.

Требование закрепления влияет и на интерфейсы.
У `Future` оно уже выражено в сигнатуре `poll`,
но у `Iterator::next` используется обычный `&mut self`.
Для обобщённой работы с неподвижными итераторами приходится обсуждать отдельный интерфейс
или изменение способа выразить неподвижность.
Эту проблему Yosh Wuyts разбирает в
[посте о `Pin` в сигнатурах трейтов](https://blog.yoshuawuyts.com/why-pin/).

### Решение: неподвижность как свойство типа

В [предложении о неподвижных типах](https://github.com/rust-lang/rust/issues/149607)
`Move` описывает разрешение перемещать значение в памяти.
Тип с `!Move` должен сохранять адрес на протяжении всего своего существования.
Компилятор проверял бы это свойство при операциях со значением.
Условия уничтожения и забывания задаются отдельно через `Destruct` и `Forget`.

В [варианте преобразования async-кода, описанном Yosh Wuyts](https://blog.yoshuawuyts.com/self-referential-types/),
компилятор сам создавал бы неподвижное состояние future.
Для нашего `OrderSubmission` соответствующая часть сгенерированного кода выглядела бы так:

```rust
// Схема будущего кода компилятора, не работающий пример на выбранном nightly.
impl !Move for OrderSubmission {}
```

Такое состояние нельзя было бы перенести в другую переменную или передать по значению в функцию.
Операции вроде `mem::replace`, позволяющие вынуть значение через `&mut`,
тоже должны учитывать ограничение `Move`.
Неподвижность была бы свойством самого значения,
поэтому API для работы с ним мог бы использовать обычные ссылки.
При работе с вложенным неподвижным значением можно было бы заимствовать его поле.

Значение с `!Move` нужно сразу создавать по адресу, который оно будет занимать до уничтожения.
Обычный возврат значения из конструктора допускает перемещение в память вызывающего кода.
Для неподвижного типа нужно гарантировать создание сразу в этой памяти.
Такое создание называют
[in-place initialization](https://blog.yoshuawuyts.com/placing-functions/).

У нынешнего future неподвижность требуется после закрепления,
а у предлагаемого `!Move` она действует с момента создания.
Поэтому добавить `!Move` к существующему async-коду и убрать `Pin` недостаточно:
нужно согласовать создание future и интерфейс его выполнения с новыми правилами.

### Статус фич

Неподвижные типы и гарантии уничтожения входят в
[принятую цель Rust на 2026–2027 годы](https://goals.rust-lang.org/2026/move-trait.html).
Дизайн ещё обсуждается.
Примеры с `MarginReservation` выше показывают обычный Rust и желаемую проверку.
Схема с `!Forget` и `!Destruct` иллюстрирует требуемые ограничения.
Синтаксис отрицательного `impl` для `Forget` приведён в цели проекта;
запись с `!Destruct` здесь показывает желаемое свойство типа.
Добавить эти строки к примеру и получить такую проверку на выбранном nightly пока нельзя.

В [предложении Niko Matsakis](https://smallcultfollowing.com/babysteps/blog/2025/10/21/move-destruct-leak/)
трейты связаны иерархией `Forget: Destruct: Move`.
Текущая цель проекта рассматривает другой вариант:
неподвижное значение тоже может нуждаться в уничтожении,
поэтому `Destruct` не должен обязательно требовать `Move`.

Изменение существующего `Future` не входит в эту цель проекта.
Переход от `Pin` к `Move` для async-кода потребует отдельного решения.

## Effects

Эффекты описывают, какие операции доступны вычислению и как оно выполняется.
В Rust так рассматривают приостановку через `.await` и вычисление в `const`-контексте.
В этом разделе нас интересует обобщение по эффектам, effect generics:
общий код, который можно использовать с разными правилами выполнения.

Побочный эффект вроде записи в файл описывает конкретное действие программы.
Здесь речь о свойствах, которые язык учитывает при проверке и вызове функций.
Например, `async` разрешает приостановку внутри функции,
но само по себе не означает, что она обращается к сети.

### Проблема: общий алгоритм для sync и async

В части 2 `ExchangeClient` задавал контракт отправки заявки.
Для симулятора отправка может быть синхронной:
он сразу возвращает идентификатор или ошибку.
Сетевой клиент возвращает future, который нужно дождаться.

Если библиотека сохраняет обе формы API,
в текущем Rust их можно выразить двумя трейтами:

```rust
trait SyncExchangeClient {
    fn submit_order(&self, order: &DraftOrder) -> Result<OrderId, ExchangeError>;
}

trait AsyncExchangeClient {
    async fn submit_order(&self, order: &DraftOrder) -> Result<OrderId, ExchangeError>;
}
```

Оба описывают одну доменную операцию.
Но алгоритм последовательной отправки пакета приходится записать для каждого контракта:

```rust
fn submit_batch<EC: SyncExchangeClient>(
    exchange_client: &EC,
    orders: &[DraftOrder],
) -> Vec<Result<OrderId, ExchangeError>> {
    let mut results = Vec::with_capacity(orders.len());
    for order in orders {
        results.push(exchange_client.submit_order(order));
    }
    results
}

async fn submit_batch_async<EC: AsyncExchangeClient>(
    exchange_client: &EC,
    orders: &[DraftOrder],
) -> Vec<Result<OrderId, ExchangeError>> {
    let mut results = Vec::with_capacity(orders.len());
    for order in orders {
        results.push(exchange_client.submit_order(order).await);
    }
    results
}
```

Порядок отправки и сбор результатов одинаковы.
Параметр `EC` позволяет менять клиента внутри каждого контракта,
но не объединяет синхронный и асинхронный варианты алгоритма.

На stable можно выбрать один async-контракт и реализовать его, в том числе для симулятора.
Его future будет возвращать результат без сетевого ожидания.
Тогда достаточно одной версии `submit_batch_async`.
Обобщение нужно, когда библиотека хочет сохранить и обычный синхронный вызов,
и асинхронный вызов с `.await`, используя общую реализацию.

### Решение: обобщить код по эффекту выполнения

В [предложении Yosh Wuyts](https://blog.yoshuawuyts.com/extending-rusts-effect-system/)
трейт, его реализации и вызывающий код могут быть обобщены по `async`.
Синхронный вариант возвращает результат напрямую,
асинхронный возвращает future с тем же результатом.

В посте для такого обобщения используется условная запись `#[maybe(async)]`.
Для нашего контракта и алгоритма схема выглядела бы так:

```rust
// Иллюстрация предлагаемого дизайна, не работающий пример на выбранном nightly.
#[maybe(async)]
trait ExchangeClient {
    #[maybe(async)]
    fn submit_order(&self, order: &DraftOrder) -> Result<OrderId, ExchangeError>;
}

#[maybe(async)]
fn submit_batch<EC>(
    exchange_client: &EC,
    orders: &[DraftOrder],
) -> Vec<Result<OrderId, ExchangeError>>
where
    EC: #[maybe(async)] ExchangeClient,
{
    let mut results = Vec::with_capacity(orders.len());
    for order in orders {
        results.push(exchange_client.submit_order(order).await);
    }
    results
}
```

Эффект функции и эффект в bound-е должны согласовываться.
Для синхронной реализации клиента компилятор создавал бы синхронный вариант алгоритма,
в котором вызов `submit_order` возвращает результат сразу.
В этой версии `.await` из общего тела не нужен.
Для асинхронной реализации сохранялось бы ожидание каждого вызова.
Это выбор при компиляции; переключения между режимами внутри цикла здесь нет.

В части 4 мы уже использовали похожее обобщение для `const`:
`ascending<T: [const] PartialOrd>` сравнивала значения при сборке и в рантайме.
Bound `[const]` требовал константную реализацию только в `const`-контексте.
Идея обобщения по `async` похожа:
писать один алгоритм для синхронного и асинхронного выполнения.

### Связь с линейными типами

У `MarginReservation` освобождение резерва может требовать асинхронного запроса.
Тогда метод `release` нужно дождаться через `.await`.
Синхронный `Drop::drop` не может выполнить такое ожидание.
Кроме того, сам future освобождения могут уничтожить до завершения операции.
Правила обязательной обработки резерва должны учитывать и такую отмену.

Расширение привычных механизмов Rust на async-код,
включая уничтожение ресурсов, входит в направление
[Just add async](https://goals.rust-lang.org/2026/roadmap-just-add-async.html).
Одного обобщения функций по `async` недостаточно,
чтобы гарантировать завершение освобождения резерва.

### Какие ещё ограничения обсуждаются

Для бэктеста полезно знать, может ли алгоритм обращаться к сети,
читать системное время или использовать внешний источник случайности.
Сегодня эти зависимости можно передавать явно через интерфейсы.
Система эффектов могла бы проверять такие свойства как часть контракта функции.

В [видении развития Rust](https://blog.yoshuawuyts.com/a-grand-vision-for-rust/)
обсуждаются детерминизм, отсутствие раскрутки стека и запрет обращений к API хоста.
Это желаемые ограничения, для которых ещё нужен дизайн.
Обобщение по `async` и `const` само по себе не даёт этих гарантий.

### Статус фичи

[Effects initiative](https://github.com/rust-lang/effects-initiative)
развивает обобщение по эффектам.
В [charter инициативы](https://github.com/rust-lang/effects-initiative/blob/master/CHARTER.md)
первоначальная задача ограничена `async` и `const`.
Там используется название keyword generics;
в последующих материалах Yosh Wuyts объясняет эту работу через effect generics.

Запись `#[maybe(async)]` выше взята из варианта дизайна,
а не из реализованного языкового API.
Окончательный синтаксис и правила обобщения по эффектам ещё обсуждаются.

## View types

View type — представление типа, в котором доступны только выбранные поля.
Ссылка на такое представление ограничивает, какие части структуры может использовать функция.
Список доступных полей входит в её контракт,
поэтому остальные поля можно заимствовать независимо.

### Проблема: метод заимствует всю структуру

В части 3 мы восстанавливали состояние заявки из журнала событий.
Теперь соберём в одной структуре журнал и книгу активных заявок:

```rust
struct ExchangeState {
    book: MatchingBook,
    journal: Vec<OrderEvent>,
    applied_events: usize,
}
```

`MatchingBook` хранит активные заявки и обновляется по событиям `OrderEvent` из части 3.
`applied_events` считает события, обработанные при восстановлении.
Начнём с пустой книги и нулевого счётчика.
Для каждого события обновим книгу и увеличим счётчик:

```rust
impl ExchangeState {
    fn rebuild_book(&mut self) {
        for event in &self.journal {
            self.book.apply_event(event);
            self.applied_events += 1;
        }
    }
}
```

Этот код компилируется на stable.
Borrow checker различает поля структуры:
ссылка на `journal` не мешает изменять `book` и `applied_events`.

Но если мы захотим вынести обновление книги в отдельный метод, то столкнёмся с проблемой:

```rust
impl ExchangeState {
    fn apply_to_book(&mut self, event: &OrderEvent) {
        self.book.apply_event(event);
        self.applied_events += 1;
    }

    fn rebuild_book(&mut self) {
        for event in &self.journal {
            self.apply_to_book(event);
        }
    }
}
```

Теперь код не компилируется:

```text
error[E0502]: cannot borrow `*self` as mutable because it is also borrowed as immutable
```

Цикл сохраняет неизменяемое заимствование `journal` для прохода по событиям.
А `apply_to_book` принимает `&mut self`, заимствуя весь `ExchangeState`.
Сигнатура разрешает этому методу менять, в том числе журнал.
Вызывающий код проверяется по этому контракту,
даже если тело метода сейчас использует только книгу и счётчик.

### Что можно сделать на stable

Передадим нужные поля отдельными аргументами:

```rust
fn apply_to_book(
    book: &mut MatchingBook,
    applied_events: &mut usize,
    event: &OrderEvent,
) {
    book.apply_event(event);
    *applied_events += 1;
}

impl ExchangeState {
    fn rebuild_book(&mut self) {
        for event in &self.journal {
            apply_to_book(&mut self.book, &mut self.applied_events, event);
        }
    }
}
```

Такой вариант компилируется.
Зависимости операции видны из сигнатуры,
и заимствование журнала не конфликтует с аргументами `apply_to_book`.
Можно также выделить книгу и счётчик в отдельный компонент с собственным методом.
View types предлагают выразить нужный набор полей без изменения состава структуры.

### Решение: указать доступные поля в типе ссылки

В [обсуждаемом дизайне](https://smallcultfollowing.com/babysteps/blog/2026/03/22/max-min-view-types-followup/)
метод может объявить, какие поля `self` он использует.
Для нашего примера один из вариантов синтаксиса выглядел бы так:

```rust
// Вариант предлагаемого синтаксиса, не работающий пример на выбранном nightly.
impl ExchangeState {
    fn apply_to_book(&mut self.{ book, applied_events }, event: &OrderEvent) {
        self.book.apply_event(event);
        self.applied_events += 1;
    }

    fn rebuild_book(&mut self) {
        for event in &self.journal {
            self.apply_to_book(event);
        }
    }
}
```

`self` в `apply_to_book` давал бы доступ только к `book` и `applied_events`.
Тип такой ссылки можно записать как `&mut ExchangeState.{ book, applied_events }`.
Поле `journal` через неё недоступно.
Обратиться к нему внутри метода или вызвать другой метод,
которому нужен доступ к журналу, компилятор не разрешил бы.

При вызове `self.apply_to_book(event)` заимствовались бы только указанные поля.
Поэтому проход по `journal` и обновление книги больше не конфликтовали бы.
Книгу и счётчик при этом не нужно копировать или переносить в другой объект.

### Статус фичи

[Эксперимент с view types](https://goals.rust-lang.org/2026/view-types-experiment.html)
принят как цель Rust на 2026 год.
В план входит реализация нескольких вариантов синтаксиса,
чтобы их можно было сравнить на практике.
Показанная запись с `.{ ... }` — один из обсуждаемых вариантов.


## Variadic generics

Variadic generics — обобщение по набору типов, количество которых заранее не фиксировано.
В каждом конкретном использовании состав и длина набора известны при компиляции.
Так можно было бы реализовать трейт для кортежей произвольной длины,
сохранив отдельный тип каждого элемента.

### Проблема: прогон проверок для кортежей разной длины

В части 3 цепочка проверок была записана через HList:

```rust
type Checks = HCons<HaltCheck,
    HCons<PriceBandCheck,
    HCons<NotionalLimitCheck,
    HCons<PositionLimitCheck, HNil>>>>;
```

У `RunChecks` было две реализации: база для `HNil` и шаг для `HCons<C, Tail>`.
Они работали со списком любой длины.
Каждая проверка получала свой контекст через `Provide<C>`,
а первый отказ останавливал цепочку.

Тот же набор типов можно записать обычным плоским кортежем:

```rust
type TupleChecks = (HaltCheck, PriceBandCheck, NotionalLimitCheck, PositionLimitCheck);
type SandboxTupleChecks = (HaltCheck, PriceBandCheck, NotionalLimitCheck);
```

Эти типы уже доступны на stable.
Но у плоского кортежа нельзя обобщённо выделить тип первого элемента и тип оставшегося хвоста,
как мы делали у `HCons`.
Для прогона приходится перечислять элементы в реализации трейта.
Например, для двух проверок:

```rust
impl<C1, C2, Ctx> RunChecks<Ctx> for (C1, C2)
where
    C1: Check,
    C2: Check,
    Ctx: Provide<C1> + Provide<C2>,
{
    fn run(order: &IncomingOrder, ctx: &Ctx) -> Result<(), Rejection> {
        C1::check(order, <Ctx as Provide<C1>>::provide(ctx))?;
        C2::check(order, <Ctx as Provide<C2>>::provide(ctx))?;
        Ok(())
    }
}
```

`<Ctx as Provide<C1>>::provide(ctx)` явно выбирает контекст для первой проверки.
Для второй используется `Provide<C2>`.
Кортежам из трёх и четырёх элементов нужны собственные реализации с тем же порядком вызовов.
Обычный параметр типа `T` не даёт способа перечислить типы внутри произвольного кортежа.

### Что можно сделать на stable

Останется рабочим HList из части 3.
Рекурсивная форма списка позволяет написать общий прогон без ограничения длины.

Если нужен плоский кортеж, повторяющиеся реализации можно сгенерировать макросом:

```rust
macro_rules! impl_run_checks {
    ($($C:ident),+ $(,)?) => {
        impl<Ctx, $($C),+> RunChecks<Ctx> for ($($C,)+)
        where
            $(
                $C: Check,
                Ctx: Provide<$C>,
            )+
        {
            fn run(order: &IncomingOrder, ctx: &Ctx) -> Result<(), Rejection> {
                $(
                    $C::check(order, <Ctx as Provide<$C>>::provide(ctx))?;
                )+
                Ok(())
            }
        }
    };
}

impl_run_checks!(C1);
impl_run_checks!(C1, C2);
impl_run_checks!(C1, C2, C3);
impl_run_checks!(C1, C2, C3, C4);
```

Макрос заменяет ручное написание каждого `impl`.
После раскрытия здесь всё равно четыре отдельные реализации для четырёх длин кортежа.
Для пятой проверки понадобится ещё один вызов макроса.
Сами `TupleChecks` и `SandboxTupleChecks` теперь можно прогонять через `RunChecks`.

### Решение: обобщить реализацию по набору типов

Variadic generics позволили бы выразить общий прогон для плоского кортежа.
В [обзоре вариантов дизайна lang-team](https://github.com/rust-lang/lang-team/blob/main/src/design_notes/variadic_generics.md)
есть предложение разбирать его на первый тип и хвост.
В этом варианте `Tuple` обозначает трейт кортежей,
а запись `(C, ...Tail)` описывает кортеж с первым элементом `C` и оставшимися элементами `Tail`.

Тогда прогон можно было бы записать рекурсивно:

```rust
// Иллюстрация одного из вариантов дизайна, не работающий пример на выбранном nightly.
impl<Ctx> RunChecks<Ctx> for () {
    fn run(_order: &IncomingOrder, _ctx: &Ctx) -> Result<(), Rejection> {
        Ok(())
    }
}

impl<C, Tail, Ctx> RunChecks<Ctx> for (C, ...Tail)
where
    C: Check,
    Ctx: Provide<C>,
    Tail: Tuple + RunChecks<Ctx>,
{
    fn run(order: &IncomingOrder, ctx: &Ctx) -> Result<(), Rejection> {
        C::check(order, <Ctx as Provide<C>>::provide(ctx))?;
        Tail::run(order, ctx)
    }
}
```

Для `(HaltCheck, PriceBandCheck, NotionalLimitCheck)` первым типом был бы `HaltCheck`,
а хвостом — `(PriceBandCheck, NotionalLimitCheck)`.
Следующий шаг проверил бы `PriceBandCheck` и продолжил с `(NotionalLimitCheck,)`.
Пустой кортеж `()` завершал бы рекурсию.

Как и у HList, состав вызовов определялся бы типом цепочки при компиляции.
Проверки по-прежнему выполнялись бы последовательно и останавливались на первом отказе.
При этом цепочку можно было бы передавать в API, работающие с обычными кортежами,
без преобразования в `HCons` и без набора реализаций для каждой длины.

Требования к обязательному составу цепочки остаются отдельной задачей.
В части 3 их выражал `Contains`.
Для представления на кортежах такую проверку тоже нужно было бы описать:
сам общий прогон не требует наличия `PriceBandCheck` и не запрещает повторить проверку дважды.

### Статус фичи

Lang-team [собирает и сравнивает варианты variadic generics](https://github.com/rust-lang/lang-team/blob/main/src/design_notes/variadic_generics.md).
Разбор на голову и хвост — один из вариантов;
обсуждаются также средства разворачивания набора типов и обхода элементов без такой рекурсии.
В [отчёте с RustWeek 2025](https://poignardazur.github.io/2025/06/07/report-on-variadics-rustweek/)
обсуждается и сложность рекурсивной модели.

В сентябре 2025 года команда запустила
[опрос сценариев использования](https://blog.rust-lang.org/inside-rust/2025/09/22/variadic-generics-micro-survey/)
для дальнейшего обсуждения дизайна и подготовки RFC.
Показанные `Tuple` и `...Tail` относятся к предложению;
окончательный синтаксис и правила variadic generics ещё не выбраны.

## Function contracts

Основной пример: резервируем `quantity` лотов из доступного объёма `available`.
Предусловие: `quantity > 0 && quantity <= available`.
Постусловие: остаток равен `available - quantity`.
Сравнить с проверками внутри функции и smart constructors из части 1.
Объяснить, почему тип ненулевого объёма не выражает отношение двух независимых аргументов.
Входящие данные сначала проходят обычную обработку ошибок;
контракт проверяет договорённости между внутренними компонентами.

Эксперимент [`contracts`](https://doc.rust-lang.org/nightly/unstable-book/language-features/contracts.html)
уже описан в Unstable Book;
[`-Z contract-checks`](https://doc.rust-lang.org/nightly/unstable-book/compiler-flags/contract-checks.html)
включает проверки в рантайме.
Проверенный вариант использует `core::contracts::{requires, ensures}`
и `move`-замыкание постусловия, которое захватывает числовые аргументы.
На выбранном nightly нарушение предусловия приводит к abort;
`Result` контракт не возвращает.
Описанные проверки не доказывают условия при компиляции.

## Unsafe fields

Пример: буфер декодера биржевых сообщений и число инициализированных байтов.
Инвариант поля: длина не превышает доступную инициализированную память.
Показать закрытый конструктор и метод изменения длины с проверкой условия.
Затем показать роль `unsafe`-поля при реализации этих методов.
Связать с приватными полями и smart constructors из части 1.
Ограничение цены или маржи само по себе не является safety-инвариантом.

Источники: [RFC 3458](https://github.com/rust-lang/rfcs/blob/master/text/3458-unsafe-fields.md)
и [tracking issue #132922](https://github.com/rust-lang/rust/issues/132922).
Минимальный пример компилируется на выбранном nightly;
компилятор помечает фичу как `incomplete_features`.

## Function delegation

Короткий раздел на примере обёртки фида рыночных данных.
Сегодня `best_bid` повторяет сигнатуру и вызывает метод внутреннего фида.
Показать, как делегирование сокращает такую реализацию трейта.
Методы, добавляющие проверки, метрики или другую логику, остаются явными.

Хорошая модель домена — это не та, где можно выразить всё подряд.
Скорее наоборот: та, в которой трудно сделать неправильную вещь.
Если модель строится вокруг примитивов и независимых полей, типы обычно позволяют больше, чем реально существует в предметной области.
Тогда ограничения начинают жить отдельно — в if-ах, документации, комментариях и негласных договорённостях вроде «этот метод не вызывай после cancel».
Получается разрыв: типы разрешают больше состояний, чем существует в модели.

Type-driven подход пытается этот разрыв закрыть.
Типы начинают описывать не только форму данных, но и правила игры: какие состояния возможны, какие комбинации допустимы, какие переходы разрешены.
У этого есть цена. Типов становится больше, модель — подробнее, а код многословнее.
Но сложность не исчезает — она просто переезжает: из runtime-проверок в систему типов.
Вместо «не забудь проверить этот кейс» появляется ошибка компиляции.
Вместо документации в духе «сюда передавай только валидное состояние» — интерфейс, который не даёт передать невалидное.
